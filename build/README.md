# build

The JavaScript side: media preparation, the sequencer, the one-file player with live and render modes, the deterministic render, the change ledger tools, the review page and the scheduler simulator. Algorithms, knobs and checks are in `references/06-layout-motion-render.md`; the ledger formats in `references/02-index-contract.md`.

## Status

Ported from the first run and wired to the project folder. Every command works on one project (the folder the intake created, holding `config.toml`), found in this order: `--project <folder>` on the command line, `SLIDESHOW_PROJECT` in the environment, or the nearest `config.toml` at or above the current directory. `SLIDESHOW_HANDOFF` and `SLIDESHOW_BUILD` override the two folders explicitly. There is no fallback into this repository: without a project every command stops with a message naming the three ways to point at one. `node lib/common.js --paths` prints what resolved.

Everything derived lands in the project's `build/` folder: `tiles/`, `clips/`, `frames/`, `audio/`, `prep-manifest.json`, `manifest.json`, `sequence.txt`, `player.html`, `player-review.html`, `review.html`, logs and renders. Asset paths inside the manifests are relative to that folder, which is where the player lives. `[tools] ffmpeg` and `ffprobe` in `config.toml` are honoured, then `<repo>/tools/ffmpeg/`, then the PATH.

- **`show.json`.** The display and taste settings come from `<project>/handoff/show.json`, which `python curate/run.py show` (and the handoff stage) derives from `[output]` and `[taste]` in `config.toml`; the contract is in `references/02-index-contract.md`. `common.js` reads it once and exports it as `SHOW`; the maximum tile and clip height for `prep` is its `taste.max_tile_height`. `build` takes the viewport, frame rate, row heights, gutter, scroll speed, background, chapters, the order (`taste.order`: `chapters`; `chronological` for one chapter; `shuffled`, a mulberry32 shuffle on `taste.seed` with each item's key replaced by its shuffled index and its year zeroed, so the date rules are inert; the report and `sequence.txt` name the mode), the moving-tile caps (`taste.moving_cap`, `taste.max_base_moving`) and `taste.mixed_tiles` (false: only featured stills are anchors, so with none every row is a base row; the video-per-row and moving-tile rules stay) from it (command-line flags such as `--speed` still win), reports which source it used, carries the numbers in `manifest.json` as before so the player and the render are unchanged in how they read them, and keeps the whole file under `show` in the manifest for the record. Without the file `build` and `render` run on the first run's defaults (2560x1440, 60 fps, medium tiles, chapters, four moving tiles, quality final, three copies) and each says so in one line, `prep` caps tiles and clips at 1640 without comment, and `add-item` says only that the off-limits list was not checked; `build` also warns when the tiles were prepared for a different maximum height (`bin/prep --force` fixes that), and stops before building (`PREP PROBLEMS`, exit 1) when a prep output failed its check (`ok: false` in the manifest, such as a clip made under the other `slow_motion` mode; `prep` itself now ends non-zero on such an output, naming how many failed and the `--force` remedy, so the two agree) or when the manifest's `slowMotion` differs from `show.json`'s while a slow-motion capture is in the set; with no such capture that mismatch is a warning. In `live_photos = "still"` mode `add-item` refuses a two-file Live Photo and a file that would pair with a row already in the set, and says to add the still alone.
- **Music.** With `show.json`'s `audio.enabled`, `prep` transcodes each file in play order to `audio/NN-<stem>.m4a` (AAC 192 kbit/s, 48 kHz, stereo, `-vn`), written under a temporary name and renamed (the stem keeps letters, digits, dot, dash and underscore and every other run of characters becomes one underscore, so the player's relative URL stays whole), skipped when present unless `--force` (`bin/prep --force --audio-only` remakes the tracks alone; `--tiles-only` and `--clips-only` limit a run the same way, `--verify-only` checks what is there and rewrites the manifest, `--dry-run` prints what every tile, clip and track would be and writes nothing, and a run with `--only <filename>` leaves the tracks alone), probes it and records `audio: [{ index, source, path, duration }]` in `prep-manifest.json`; a file ffmpeg cannot decode is a FAILED line. `build` puts `audio: { enabled, files, loop, volume }` in `manifest.json`, enabled only when `show.json` and the prep manifest agree, else off with a warning (a `volume` above 1 reaches the rendered file only; the player's element ends at 1); the live player plays the files in order through one `<audio>` element, restarts the list when `loop` is on, starts at once where the browser allows sound without a gesture (the browser launchers' kiosk flag does) and otherwise on the first key press or click (the HUD reads "music: press any key" until then), mutes and unmutes on M, pauses with the scroll on space, and ignores speed changes; render mode plays nothing, and the review page needs nothing. `render` still renders and verifies a silent file, named with `-silent` before `.mp4` (`slideshow-silent.mp4`, `test-5s-labels-silent.mp4`), then joins the tracks with `acrossfade` of `crossfade_s` into `audio/playlist.m4a` once per render (a single track is copied; a junction whose neighbour is not longer than the crossfade falls back to a plain concat, and the log names that junction, the track and the reason), cuts a soundtrack of the video's length (the playlist looped with `-stream_loop -1` when `loop` is on, `volume`, `afade` in from 0 and out to the end over `fade_s`, skipped when it is 0), muxes it on under the plain name with both streams copied (`-shortest`, faststart), and logs the soundtrack duration, the fades and a final probe: an audio duration more than 0.5 s off the video's is a PROBLEM. `render --concat` joins the silent copies and muxes one soundtrack of N times the loop over the whole file, `slideshow-x<N>.mp4`, so the music runs across the seams. Nothing happens when audio is disabled, and the names are as in 0.2.
- **Slow motion.** `show.json`'s `taste.slow_motion`: `slow` (a clip captured at 100 fps or more plays slow; the `"realtime": []` list in `prep-options.json` names exceptions) or `realtime` (every such clip at real time; the `"slow": []` list names exceptions). `prep` looks for `<project>/prep-options.json` first, then this folder's `prep-options.json`, and its report names the mode and the exceptions.
- **HEIC without `sips`.** Still-image facts (displayed and stored dimensions, orientation, DateTimeOriginal) and JPEG conversion go through `common.imageInfo` and `common.makeJpeg`: JPEG in pure JS, `sips` on macOS as the fast path for JPEG, HEIC, HEIF and PNG, otherwise `curate/heic.py` (pillow-heif) run with the repo's `.venv` Python; a webp goes through `heic.py` on every platform. The accepted extensions are the same lists as `curate/common.py`. `sips` output keeps the pixels stored-rotated with the orientation tag; `heic.py` writes them upright with the tag cleared and the rest of the EXIF carried across. The tile verification accepts both.
- **Stable identity.** `media_id` (SHA-256 of the bytes) is the first column of `media.csv` and `cut-list.csv`. `add-item` computes it for every file it adds and fills it in on rows that still lack one; the column is inserted at the front if a file predates it. New rows carry `date_source` (`owner` by default, `--date-source` to override) and `date_witness` (`--witness "<sentence>"`). `changes.log` lines follow the contract's format exactly (`add`, `remove`, `cut`, padded to eight columns; a `pair` line records a plain still upgraded to a Live Photo still by a later-added companion). After hashing each input, `add-item` refuses a file whose `media_id` or name (as given, bare, or the new dated name, case-insensitively) is in `show.json`'s `off_limits`, with exit 2 and nothing written: "`<name>` is on the off-limits list ([show] off_limits in config.toml); not added". A dry run reports the same. Without `show.json` there is no off-limits check, and it says so in one line. `apply-replacements` runs `add-item` per row, so a replacement round gets the same refusal.
- **Write-back.** `apply-replacements` copies the current `media.csv` and `changes.log` into the round folder on every run, success or stop; a dry run writes them to `<folder>/dry-run/`. The round always carries the live index home.
- **Browser.** `render` and `simsched` try, in order, `[tools] chrome` from `config.toml` (when set and the file exists), Playwright's bundled Chromium, and installed Google Chrome (`channel: 'chrome'`), logging which one started and every attempt that failed before it. Install the bundle with `npx playwright install chromium` inside `build/`.
- **Render flags.** `render --labels` draws the review labels into every frame (per tile the id and `date · kind`, per row `row · chapter · type · t=`) and adds `-labels` before `.mp4`, for an owner who is not at the machine; the launchers never pick that file up. `render --concat` (`--x3` still works) also writes `slideshow-x<N>.mp4`, N copies of the loop back to back, N from `show.json`'s `output.concat_copies` (3). The x264 preset and crf come from `output.quality` (`final`: slow, 18; `draft`: veryfast, 23); `--preset` and `--crf` still override, and the log line names the preset. The verify is unchanged: size and frame rate come from the manifest. With `show.json`'s `machines.player` at `tv-usb`, `render` adds `-profile:v high` and a level (4.1 for 1920x1080 and under at 30 fps and under, 4.2 for 1920x1080 and under above 30 fps, 5.1 above 1080p) to the x264 arguments and logs it, and warns after every final file, the concat included, when it is 4 GiB or over, since FAT32 sticks refuse such files; a warning, not a failure. `render --dry-run` prints the whole plan - the frame count and length, the silent and the muxed output name, the tv-usb level, the playlist with every junction, the soundtrack and every ffmpeg command it would run, the concat included - and writes nothing at all: no frame sequences, no mp4, no playlist, no soundtrack, no render log. A muxed file that fails its probe does not keep a name a launcher plays: it is renamed `BAD-<name>.mp4` (`BAD-slideshow.mp4`, `BAD-slideshow-x3.mp4`) and the PROBLEMS lines name it under that name; when the mux itself fails, nothing is written under the plain name, so a file of that name left by an earlier render is renamed `OLD-<name>.mp4`. Both are logged and the run still exits 1.
- **Windows.** Every command has a `bin/<name>.cmd`; `prep`, `build`, `add-item`, `frames` and `render` run under `bin/keepawake.ps1`, which holds the machine awake through `SetThreadExecutionState` for as long as the command runs (display too for `render`), the way the POSIX wrappers use `caffeinate`. `live.cmd` and `review.cmd` open the pages in Chrome. The `.cmd` files are CRLF on purpose.
- **Not yet tested on this port:** the macOS `sips` and `caffeinate` paths and the `.command` launchers on a real Mac, the Windows `.bat` launchers on a real desktop, and playback on a real TV stick. The pure-JS, Python and CSV paths were exercised on Windows against a synthetic project (path resolution, `prep` tiles for JPEG, PNG and HEIC, `build`, `add-item` with a HEIC swap, `apply-replacements` with write-back, `redate` dry run, and the `.cmd` wrapper with the keep-awake); what each version's smoke test covered on Linux, the render included, is in `CHANGELOG.md`.

## Layout

```
build/
  package.json            Playwright pinned
  lib/                    build.js, prep.js, render.js, frames.js, add-item.js, apply-replacements.js,
                          redate.js, review.js, candidates.js, simsched.js, common.js
  bin/                    one wrapper per command, POSIX and Windows: prep build add-item apply-replacements
                          redate render frames review candidates live simsched, plus keepawake.ps1
  player.template.html    the player; build.js inlines the manifest into it to produce <project>/build/player.html
  launchers/              desktop launchers for macOS and Windows. The VLC ones (start-slideshow.command and the -usb
                          pair) play the first slideshow-x*.mp4 in name order, else slideshow.mp4, from $SLIDESHOW_FILE or
                          beside the script (the plain .command also tries ../build and any mounted USB stick), without
                          muting; start-slideshow-browser.command and .bat open player.html (beside the script, ../build,
                          or $SLIDESHOW_PAGE; it must sit in its build/ folder, since the page's tiles, clips and music are
                          relative paths) in Google Chrome kiosk mode on a profile of its own, autoplay allowed (under
                          caffeinate on macOS)
  overrides.example.json  copy to <project>/overrides.json (or build/overrides.json here, gitignored) for
                          per-item start and trim overrides
  prep-options.json       per-file preparation switches (the realtime and slow lists); <project>/prep-options.json wins when present
```

Each wrapper puts an optional local toolchain (`<repo>/tools/node`, `<repo>/tools/ffmpeg`, both gitignored) on the PATH and runs the matching script in `lib/`. Usage: `bin/build --project <folder>` (or `bin\build.cmd` on Windows), and likewise for the rest.
