## 0.4.1, 2026-09-16

A fix release over eleven files. No new setting, no column moved, nothing in `config.toml` that was not there before.

The EXIF rung used to take whichever EXIF time it found first, `DateTime` (tag 306) included, and to copy the raw value into `exif_datetime_original` as though it were a capture time. Tag 306 is a modification stamp, so a scan or a re-export dated the photo by the day it was edited, and the column then presented that to every later gate as the file's own intact metadata. The probe now records which tag a time came from (`exif_dt_tag`, `curate/stages/_probe.py`) and beside it the raw `DateTimeOriginal` as shipped, or `DateTimeDigitized` when there is no original (`exif_capture_raw`); the index takes `DateTimeOriginal` or `DateTimeDigitized` as the capture time and says in the witness when the value came from `DateTimeDigitized` because the file has no usable original; and tag 306 becomes a rung of its own below the owner's priors, `date_source` `exif-modified`, precision day, with a witness saying the stamp is not a capture time and that the file carries no usable `DateTimeOriginal` or `DateTimeDigitized`. The `exif_datetime_original` column is keyed on the tag and not on the parse: what those two tags shipped stays there whether or not it reads as a date, which is how validate's bogus-timestamp gate still sees a zeroed `0000:00:00 00:00:00` clock, while a tag 306 value never reaches the column at all. Gate 3 cannot fire on an `exif-modified` row either way, because no capture-class value on it parses into a date to disagree with. validate gains an `exif-modified` gate, severity `warn`, which asks the owner to confirm the date on the contact sheet or to declare it with a witness. A probe cached before the tag and the raw capture value were recorded is probed once more, and the stage prints how many, once. One more index fix rides along: `best_frame_distance` returned a two-tuple when ffmpeg exited non-zero, while the index unpacks three values, so a single clip ffmpeg could not decode ended the whole stage with a `ValueError`. That one path returns a triple now, which is what every other way out of the function already did, and a clip that will not decode is simply no frame witness.

A Takeout zip member that is neither media nor a readable sidecar used to vanish: nothing extracted it and nothing counted it. `zip_members` returns those members with a reason now, and ingest writes `index/skipped-members.csv` with the columns `zip`, `member`, `bytes`, `extension` and `reason` (`not-media`, or `json-too-large` for a `.json` over the 64 000-byte sidecar limit) and names the count and the breakdown by extension on that zip's own line, `5 members skipped (not media or sidecars): .aae 1, .html 2, .json over 64 000 bytes 1, .txt 1; listed in index/skipped-members.csv`, which reads "would be listed in" on a dry run, where nothing is written.
