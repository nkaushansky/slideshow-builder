# Layout, motion and render

The build takes the frozen set and produces a browser player and a rendered video. Everything that moves is a pure function of elapsed time computed in the player's script, never a CSS animation, so the live player, the render and the scheduler simulator agree frame for frame. The numbers below are the first run's defaults; the intake and the owner's live-player round tune them. The display and taste numbers (resolution, frame rate, row heights, gutter, scroll speed, background, the order, the moving-tile caps, the seed, the Live Photo and slow-motion modes) and the music reach the build through `handoff/show.json`, derived in Python from `[output]`, `[taste]` and `[audio]` in `config.toml` (`02-index-contract.md`); without that file the build falls back to the first run's values and says so.

## Output target

Render at the display's **logical** resolution (2560×1440 for a 27-inch 5K panel; 1920×1080 for most TVs), at the configured frame rate, H.264, silent; when `[audio]` is enabled the soundtrack is muxed onto the verified silent render afterwards. The target is `[output]` in `config.toml`, read through `show.json`: `resolution` (Step 0 detects the build machine's display; a different display machine is the intake's answer), `fps` (60, or 30 to halve the render time and suit TVs and older laptops), `quality` (`final`: x264 slow, crf 18; `draft`: veryfast, crf 23, for quick test renders) and `concat_copies` (3). At viewing distances of five feet or more the eye cannot resolve more than the logical resolution, and a native-5K render would quadruple render time and exceed hardware-decode limits on older machines. The deliverable is an mp4 that loops in VLC, or plays from a USB stick on a TV (`[machines] player = "tv-usb"` picks the H.264 profile and level such sticks decode); the browser player exists to produce that mp4 deterministically and to serve as a live fallback, with kiosk launchers of its own. `[show] playback = "once"` makes that file a show that ends: the title card, one loop, the end card, and `build/playback.txt` telling the launchers not to repeat it.

## Items and dates

- A Live Photo pair is one item; the video half is what is displayed. The still is never shown (switching between still and video pops, and at tile size the video frame is sharp enough). With `[taste] live_photos = "still"` the clip never reaches the build: select cuts it and the still stands alone as a plain still.
- Ordering key: day precision uses the date; month precision the 15th; year precision July 1; ties by filename. Nothing displays a date.

## Sequence: mini-timelines

Viewers glance for a minute or two, so every two-minute window should span the whole range rather than one era.

1. Sort all items by date key.
2. Deal round-robin into `chapters` (default 10) so each chapter has about the same count and runs the whole span. Deal stratified: standalone videos, featured stills, other moving items and plain stills each dealt round-robin by date with one running cursor, so no chapter ends up with all the videos. This is `[taste] order = "chapters"`. `chronological` sets one chapter: the whole span once, then the wrap. `shuffled` shuffles the items with a seeded PRNG (mulberry32 on `[taste] seed`) before the deal, replaces each item's ordering key with its zero-padded shuffled index and zeroes the year the spacing rules read, so the chronology penalty and the pull gap are inert and the chapters, as configured, are dealt from the shuffled order; the same seed gives the same sequence. The report and `sequence.txt` name the mode; command-line flags still override.
3. Concatenate. The sequence is a **ring**; the wrap from the last chapter to the first is just another chapter boundary, which is what makes the loop seam invisible.
4. Spacing pass, within a chapter only: standalone videos never in adjacent rows if the chronology allows (`videoMinRowGap` 2), no base row with more than 2 moving tiles, nudges within `anchorLookahead` positions except videos, which may move up to `videoNudge` (12). Deterministic greedy search.
5. **Chronology beats spacing.** A quadratic penalty (`disorderWeight` 2000) for any backward jump over half a year between neighbours means videos barely move and video rows are often consecutive; the owner on the first run preferred that to items pulled years out of order. Print the trade-off (adjacent video-row pairs versus backward jumps) for two or three weights and let the owner choose; one build prints those numbers for the weight it ran with, so two or three of them means running `bin/build --disorder N` two or three times.
6. **Rows never straddle a chapter boundary.** A rebalancing pass shifts items between neighbouring rows of the same chapter to even heights; chapter tails are pooled and re-split. The reset from the last year to the first is a clean row-to-row cut.
7. A fixed `seed` (`[taste] seed`, 20260905) for any randomness, so the sequence is reproducible and reviewable; only the shuffled order uses it.

Loop length is an output: item count, scroll speed and the share of feature rows set it. Expect about 2 seconds per item at 100 px/s on 1440 rows with the default row mix: the first run's 469 moments made a 15-minute loop, 2.2 seconds per item at medium tiles. The pace scales with the screen height, so the seconds per item hold on any display, and the select stage sizes the cut from that figure, scaled by the tile size and the scroll speed (`04-selection-lenses.md`).

## Layout: justified rows

- Rows span the full width. Each item is scaled to the row's target height at its own aspect ratio; items are pulled until the row is full; the row is scaled to fill the width exactly. **No cropping, ever**, except for the rounding: the row height and every tile width are whole pixels, the last tile of a row takes whatever the rounding left so the row ends exactly at the edge, and tiles are drawn to cover their box in the page and in the rendered canvas alike, so a tile can lose a pixel or two of its edge. Nothing is composed away; there is no crop to a different aspect. An item wider than about 2.4:1 takes a row alone.
- Two row types: **base** (`baseRowHeight` 520 px, typically 4 to 5 items) and **feature** (`featureRowHeight` 820 px, 2 to 3 items). The heights come from `[taste] tile_size` as a share of the screen height: `small` 0.28 and 0.44, `medium` 0.3611 and 0.5694 (520 and 820 at 1440 rows, the first run's), `large` 0.46 and 0.72 for a wall seen from across the room; each rounded to an even pixel count. `[taste] base_row_height` and `feature_row_height` in pixels override the preset. A row ends when its natural width crosses the screen; the straddling item joins unless that makes the row more than `fillBias` (0.1 in log-height) worse than stopping, so rows err short.
- **Anchors** = the featured stills plus every standalone video. A Live Photo takes its featured mark from its still, and the video half is the item that is displayed, so a featured Live Photo arrives as a moving anchor and starts a feature row like any other. When the next item is an anchor, start a feature row; fill it by pulling further anchors from within `anchorLookahead` (6) positions, otherwise the next items in sequence. **Max one video per feature row.** With `[taste] mixed_tiles = false` only featured stills are anchors, and since select then makes none, every row is a base row with the videos in the grid; the one-video-per-row and moving-tile rules still hold. Count the videos a row already holds, not the anchors: with mixed tiles off a video arrives as a plain item, either in the stray items folded into the row ahead or in the pull that fills an underfilled base row, and a rule that looks only at anchors lets a second one in and fails the acceptance check afterwards.
- Any pull is allowed only if the pulled item is at most `pullMaxGap` (1.25 years) ahead of the item it jumps past; the owner flagged featured stills pulled a year and a half forward as out of place.
- **Do the anchor arithmetic before building.** Anchors ÷ items sets the feature-row share. On the first run 129 anchors among 469 items (75 featured stills plus 54 videos) gave 83 feature rows of 134, or 62 percent, and a 15-minute loop where 12 had been expected. Print row counts and the share on every build.
- `gutter` 8 px at 2560 wide, scaled with the width and never under 4; background `[taste] background`, a near-black (`#07070F`) chosen to match the event's identity, painted on the page and the stage and behind every rendered frame.

## Media preparation

- **Stills:** HEIC and webp to JPEG at quality 90, then every still resized to a maximum height of twice the feature row (`max_tile_height` in `show.json`; 1640 px at 2560×1440 medium). Compute the resize from the index dimensions, not from the file, because some tools keep rotation as a tag rather than rotating pixels. Use Pillow with its HEIC plugin so the step works on every platform (`sips` on macOS for JPEG, HEIC and PNG only). A display or tile-size change after preparation means `bin/prep --force`; `bin/build` warns when the prepared cap disagrees with `show.json`.
- **Clips for live mode:** every Live Photo video, standalone video and GIF to H.264, `-preset veryfast -crf 20 -pix_fmt yuv420p`, no audio, faststart, display height capped like the stills. Do not rely on the browser's HEVC support.
- **Music:** with `[audio]` enabled, each file in play order is transcoded to `build/audio/NN-<stem>.m4a` (AAC 192 kbit/s, 48 kHz, stereo, no video; the stem keeps letters, digits, dot, dash and underscore, anything else becomes an underscore), written under a temporary name and renamed, skipped when present unless `--force` (`bin/prep --force --audio-only` remakes the tracks alone), probed, and recorded in the preparation manifest with its duration; a file ffmpeg cannot decode is a FAILED line. Nothing happens when audio is disabled, and `--dry-run` prints the track list with what each one would be without touching them.
- **HDR:** 10-bit HLG or PQ videos come out washed out; tone-map to SDR BT.709 (`zscale` plus `tonemap=hable`, chosen on a contact frame over mobius and clip). The index sets the `hdr` flag on a transfer of `smpte2084` or `arib-std-b67` or on any pixel format whose name contains "10", which also catches a 10-bit SDR clip, so a few files are tone-mapped that did not need it.
- **Slow motion:** videos captured at 100 fps or more play at 30 fps, which is the capture rate over 30: eight times slow at 240 fps, four times at 120, as the phone shows them; record the effective duration in the preparation manifest. `[taste] slow_motion` picks the mode: `slow` is this, with the `"realtime": []` list in `prep-options.json` naming clips that play at real time anyway; `realtime` plays every such clip at real time, with the `"slow": []` list naming the exceptions. `<project>/prep-options.json` is read first, then the repository's `build/prep-options.json`; the prep report names the mode and the exceptions, and `HANDOFF.md`'s slow-motion line names the mode in force.
- **Frames for render mode:** per placement, JPEG frames at 30 fps scaled to the row height the item landed in; Live Photos and GIFs in full; standalone videos from their `start` offset for the visible window plus one second. For slow motion use `setpts` with constant-rate output, and give the `-t` window in **display** seconds, because an output-side `-t` is measured after `setpts`. Padding a missing frame or two is allowed; past a threshold of 30 the step fails and reports, and a sequence padded by more than three is named in the report. A completion marker records the frame count, the files written, the window, the row height and the slow-motion factor. The goal is to **verify by distinct frames**, because a stalled decoder can repeat one; what this version verifies is the file count against the count the placement needs, plus that padding threshold, and it never compares frame contents.
- Preparation is idempotent: outputs written under a temporary name and renamed, so an interrupted run resumes. Wrap it in the OS keep-awake tool. `bin/prep --dry-run` rehearses it: the set is verified, the clips are probed, and every tile, clip and track is printed as it would be handled (made, skipped because it is already there, remade under `--force`, or a missing source), with nothing written at all - no outputs, no manifest, no report, no log. A real run ends non-zero when any output failed its verification, naming how many and pointing at `bin/prep --force` (`--force --audio-only` for a track), because `bin/build` refuses to build on an output recorded `ok: false`.

## Motion rules

- **Live Photos and GIFs:** play the full clip forward, no trim, hold the last frame for `livePhotoHold` (1.5 s), then restart. No ping-pong. Per-file trims exist and default to zero; change them only after the owner's review.
- **Standalone videos:** feature rows only, one per row, muted, a per-file `start` offset defaulting to zero, playing for the whole time the row is visible (about 23 s at 100 px/s) and looping if shorter. No pausing the scroll, no promotion to full screen.
- **Moving-tile cap:** at most `movingCap` (4) tiles animate at once, and no base row holds more than `maxBaseMoving` (2); `[taste] motion_density` sets the pair: `calm` 2 and 1, `normal` 4 and 2, `busy` 6 and 3. A scheduler grants a slot when a moving tile enters the viewport and releases it on exit; a tile without a slot shows its first frame. Grants are deterministic from the clock so live and render agree. Rules that the owner's review produced on the first run and that should be defaults: `videoPriority` (a video entering the viewport takes a slot from the longest-running Live Photo that has finished a play); `rotateSlots` with `rotatePlays` 1 (a Live Photo that has played once hands its slot on when another is waiting); `maxWait` 4 s; `startVisibleFrac` 1 (a Live Photo asks for a slot only once its row is fully on screen, a video asks the moment any of it appears). A scheduler simulator steps a loop in a fraction of a second and prints wait percentiles and how many first plays were cut short; use it instead of watching loops to answer scheduling questions.

## Player

One HTML file opened from `file://`, manifest inlined as a script array because `fetch` is blocked on `file://`. Scroll position is `scrollSpeed × t`; rows are positioned from it and recycled through the ring so memory stays flat. The stage is sized from the manifest's viewport and painted with its background at startup; nothing in the page is hard-coded to 2560×1440, and the review type scales with the height (19 and 22 px at 1440). Two modes: `live` (muted video tiles, the scheduler) and `render` (moving tiles are image elements whose source is the frame index for the clock; no video elements). The manifest carries `audio` (`enabled`, `files`, `loop`, `volume`), enabled only when `show.json` and the preparation manifest agree, else off with a build warning. With it enabled, live mode plays the prepared tracks in order through one audio element, moving to the next when one ends and restarting the list when `loop` is on, at the configured volume (an audio element's volume ends at 1, so a `volume` above that reaches the rendered file only). It starts at once where the browser allows sound without a gesture (the browser launchers' kiosk flag does); where the browser blocks it, it starts on the first key press or click, and until then the HUD reads "music: press any key". Pause pauses the music with the scroll; speed changes leave it alone; render mode plays nothing. Keyboard in live mode: fullscreen, pause, speed up and down, M to mute and unmute. Review aids behind URL parameters only: labels, click-to-flag with notes persisted locally, a start time. In render mode `?labels=1` draws the same labels into every frame: per visible tile a translucent dark box at its bottom-left with the id on one line and `date · kind[ · featured][ · slow-mo]` on the next, per visible row a tag at its top-left reading `row i · chapter n · type · t=MmSSs`; nothing is drawn without the parameter. A review page lists the whole sequence with thumbnails, names and entry times.

**Cards in the page.** The manifest carries `playback` and `cards` (`title`, `end`, `seconds`, `fade_s`) from `show.json`. In live mode a title card holds for `seconds`, fading in and out over `fade_s`, before the scroll starts; the clock waits with it, so the loop is unchanged. With `playback = "once"` the scroll stops after exactly one loop and the end card holds and freezes there, and the music pauses once the card is fully in; with no end card the page freezes on the last frame and the HUD says "the end" for a moment. Under `playback = "loop"` the scroll never stops and no end card is drawn, because a looping show never reaches one. `?card=title` and `?card=end` show that card alone, full screen, at full opacity, with the stage and the HUD hidden, and set `window.__cardReady` once the fonts have settled: that is the page the render photographs. A card is the show's background with its lines centred, at 96 px on 1440 rows, scaled with the height like the labels, so it reads the same on any display. The flagging page (`player-review.html`) neither holds a card nor stops, so look at the cards in the live player or at `?card=`.

**Captions in the page.** With `[taste] captions = "date"` every tile carries its own date at its own precision (`2019`, `June 2021`, `June 15, 2021`); with `"text"` it carries the `caption` column of `media.csv`, and nothing when that is blank. The caption is one line in a bar at the bottom of the tile, ellipsised at the tile's width, at 22 px on 1440 rows and scaled with the height; with `?labels=1` it moves to the top of the tile so the review label keeps the bottom. It is a DOM element on the page for the live player and the flagging page, and the render's canvas paints the same bar itself (ellipsised by measuring the text, since a canvas has no CSS to do it), so the caption is in the rendered file as well.

## Render

- A headless browser driven by Playwright (`[tools] chrome` from `config.toml` when set and present, else bundled Chromium, else installed Chrome via `channel: 'chrome'`), viewport at the output resolution, device scale factor 1, page served over local HTTP because images loaded from `file://` taint a canvas.
- Per frame, the script calls the page with the exact time (k × 1000/fps): the page sets its clock, updates rows and the scheduler, draws every visible tile into a canvas the size of the viewport, JPEG-encodes it and sends it over a WebSocket to the script, which pipes it into ffmpeg (`image2pipe`) and acknowledges once ffmpeg accepted it, so the page never runs ahead. **Why not screenshots:** the browser's screenshot path cost about 350 ms per frame on the first run's hardware, five hours per loop; the canvas path cost about 85 ms. Measure at Step 0.
- Before frame 0, step the scheduler through whole loops without drawing and compare a canonical snapshot of its state loop to loop, so frame 0 carries the periodic state and the wrap is seamless. The count is a fixed number of loops (`--warm-loops`, 8) rather than a wait until the state repeats: the log says whether the last two loops matched and from which loop the state began repeating, and a state that never repeated is a warning that names a larger `--warm-loops` and `bin/simsched`, not a stop, because the wrap check below is the backstop. Then render **exactly one loop**: frame count = loop seconds × fps, frame 0 being the frame that follows the last. Check the wrap by PSNR between frame 0 and the frame after the last: it passes at `inf` or at 40 dB and above, where nothing is visible at the seam, and it is enforced only on a full loop, a windowed render saying in its log that the wrap closes only on one. When that PSNR falls below 40 dB on a full loop, the render crops both frames to each visible tile's own box, every edge floored to an even number because ffmpeg's psnr filter will not measure an odd box on a 4:2:0 frame, and logs the three tiles that differ most, worst first with their dB, and says what the worst one means: a moving tile that far off is the frame index of its clip landing one frame out across the seam, which the log calls a rounding problem in the player's `frameIndexFor`; a still is a scroll that did not wrap on the pixel, which is `loop.height` and `loop.speed` in `build/manifest.json`; and a moving tile whose frame index did not slip gets that scroll hint too, since the scroll is then the likelier cause. The PROBLEMS line names the worst tile. One exact check stands beside that picture test, because two frames of one clip can look alike and hide a one-frame slip behind a PSNR of inf: the render asks the page for every visible moving tile's frame index at frame 0 and again at the wrap and warns about any tile that does not restart on the frame it began on, naming it. That one is a warning and not a problem, because identical pixels mean the owner sees nothing. Both are about the epsilon in the player's `frameIndexFor`, which floors `pos * FPS + EPS` so that the warm-up and the render, which reach a frame boundary by two routes that round the last bit the other way, show the same frame.
- Encode `libx264 -pix_fmt yuv420p` at the output frame rate, preset and crf from `[output] quality` (`final`: `-preset slow -crf 18`; `draft`: `-preset veryfast -crf 23`; `--preset` and `--crf` override), full-range JPEG converted to limited-range BT.709 and tagged. The log line names the quality preset. With `[machines] player = "tv-usb"` the arguments add `-profile:v high` and a level: 4.1 for 1920×1080 and under at 30 fps and under, 4.2 for 1920×1080 and under above 30 fps, 5.1 above 1080p, logged; and after every final file (muxed or not, the concat included) a file of 4 GiB or over gets a warning that FAT32 sticks refuse it (use quality draft, fewer concat copies, or an exFAT stick). A warning, not a failure.
- **Cards as segments.** A card is never painted over the mosaic. The loop's frames are the ones the wrap proof compares (frame 0 against the frame after the last), so anything drawn into them would break that proof and shift every frame's timing; each card becomes its own short segment instead and the three parts are joined by copying. Only a full-loop render assembles cards: with `--seconds` or `--from` the loop is rendered exactly as before, and a title card that is being left out is named in the log (`cards: skipped (they go on a full-loop render only)`). A `--labels` render is a full loop like any other, so it does get the cards, photographed from the card page, which carries no labels. With a card set, the frames go to the plain name with `-loop` before `.mp4`; once that file passes its verify and its wrap check, each card is screenshotted from the player's own card page (`player.html?card=title`, at the output size, after `window.__cardReady`), checked against the text in the manifest, written to `build/cards/<stem>-<which>.png`, and encoded from that still to `build/cards/<stem>-<which>.mp4` with the loop's own settings - the same size, frame rate, pixel format, preset and crf, and the `tv-usb` profile and level when that player is set - holding `round(card_seconds × fps)` frames with a fade in and out over `fade_s`. Title, loop and end are then concatenated with `-c copy` into the name the loop render would have had, the joined file is probed, and the `-loop` file is removed only once its frame count equals the loop's plus the cards'. A missing screenshot, a card whose text does not match the manifest, a failed encode, a failed join or a wrong count is a PROBLEM and the loop file stays. `--concat` with `playback = "once"` is refused, naming both: copies of a show that ends are not a show. An end card set under `playback = "loop"` is dropped here as it is in the page, so a looping file is assembled as title plus loop and each concat copy carries the title card. `--dry-run` prints each card, its text, its frames and the join without writing.
- **Soundtrack.** The render itself is unchanged and its verify still requires no audio on the file it just made. With `[audio]` enabled, after the verify passes: the prepared tracks are joined once per render into `build/audio/playlist.m4a`, consecutive tracks crossfaded over `crossfade_s` (when it is above 0 and both neighbours are longer than it; a single track is copied); the soundtrack's duration D is the assembled file's, cards included, not the loop's; it loops the playlist when `loop` is on (else it plays once), is cut at D, gets `volume`, a fade-in of `fade_s` from the start and a fade-out of `fade_s` ending at D (no fade when `fade_s` is 0; when the playlist is shorter than D and `loop` is off, the fade-out sits at the playlist's end and the log says the music ends early); the mux copies both streams whole, with faststart and no `-shortest`: the soundtrack is already cut and padded to exactly D, so the flag guarded nothing, while AAC's priming samples put the end of the audio stream about a tenth of a second before the end of the video in the container's timeline, which `-shortest` read as the end of the file and trimmed the last video frames from. The verified video-only file keeps its usual name with `-silent` before `.mp4` (`slideshow-silent.mp4`, `test-60s-labels-silent.mp4`) and the muxed file takes the plain name, so the launchers pick up the one with music; without audio the names are as before. The playlist line names every junction that fell back to a plain concat and why (the track that is not longer than the crossfade, or `crossfade_s` being 0), so a hard cut is never silent in the log. The log names the soundtrack duration, the fades and a final probe of the muxed file (codec, channels, duration), which is checked three ways: every frame of the silent file is still there, the audio is within 0.5 s of D, and the file's own length is too, which is the bound `-shortest` used to give. Any of the three is a PROBLEM, and the file that failed is renamed `BAD-<name>.mp4` at once, because the launchers play `slideshow-x*.mp4` and `slideshow.mp4` and neither may be a file that failed its check; when the mux itself fails nothing is written under the plain name, so a file of that name from an earlier render is renamed `OLD-<name>.mp4` for the same reason. Both moves are logged with the new name, and the run ends non-zero either way. `bin/render --dry-run` prints the whole plan - frame count and length, the silent and the muxed name, the playlist junctions, the soundtrack filters and every ffmpeg command, the concat included - and writes nothing, not even the render log.
- **Always a 60-second test render first**, then window renders (`--from <seconds>`) around every special case. Only then the full render. `--labels` renders with the review labels drawn in and adds `-labels` to the file name, so an owner who is not at the machine can name any tile from a test render; the launchers never pick that file up. Expect one to three hours on 2017-era hardware for a 15-minute loop; log the rate.
- `--concat` (`--x3` still works) concatenates `[output] concat_copies` copies (3) with stream copy into `slideshow-x<N>.mp4`, so the player's own loop seam lands every 45 minutes rather than every 15. With music it joins the silent copies and muxes one soundtrack of N × D over the whole file, so the music runs across the seams. The launchers look for `slideshow-x*.mp4` first, then `slideshow.mp4`. Soak in VLC for the length of the event window and read its log for late frames. Then the owner's full watch.
- Playback: VLC, repeat one, fullscreen, OSD off, and on macOS under `caffeinate`, which the three `.command` launchers run the player inside; the Windows `.bat` launchers hold nothing awake and say in their own comments to turn screen sleep off in the power settings first. The launchers do not mute, so a silent file plays nothing and a file with music plays it at the venue's volume; the Mac's `start-slideshow.command`, which kills any running VLC and starts the file, looking beside itself, then in the project's `build/`, then on any mounted USB stick, while the two USB editions and the Windows `.bat` play only what sits in their own folder; a TV playing the file from a stick; the browser launchers (`start-slideshow-browser.command`, `.bat`) that open `player.html` (beside the script, in `../build`, or `$SLIDESHOW_PAGE`; it must sit in its `build/` folder, because the page's tiles, clips and music are relative paths) in Google Chrome kiosk mode on a profile of its own, autoplay allowed, under caffeinate on macOS, with a clear message when the page or Chrome is missing, as the last resort.

## Tuning knobs

One config block at the top of the build script. `tile_size`, `scroll_speed`, `background`, `chapters`, `gutter`, `order`, `motion_density` (`movingCap` and `maxBaseMoving`), `mixed_tiles`, `slow_motion` and `seed` come from `config.toml` through `show.json` (`chapters` when not 0; `gutter` is derived from the width), taking effect on the next `python curate/run.py show` and `bin/build` (`bin/prep --force` after a change to `slow_motion`: `bin/build` stops on a clip that failed its prep check or on a manifest prepared under the other mode while a slow-motion capture is in the set, so a stale clip never reaches the player); the rest are the script's own defaults. Command-line flags (`bin/build --speed 120`, `--base-height`, `--feature-height`, `--lookahead`, `--pull-gap`, `--disorder`, `--video-nudge`, `--start-visible`) beat both for a quick try:

| Knob | Default | Trade-off |
|---|---|---|
| `tile_size` (`baseRowHeight`, `featureRowHeight`) | `medium` (520, 820 at 1440 rows) | `small`, `medium`, `large` as shares of the screen height: tile size against items per screen; `base_row_height` and `feature_row_height` in pixels override |
| `scroll_speed` (`scrollSpeed`) | 0 = 100 px/s scaled to the height | slower reads easier and lengthens the loop; the owner compared 100 and 120 by eye |
| `background` | `#07070F` | near-black; matched to the event's identity |
| `chapters` | 10 | shorter chapters sweep the span more often but hold fewer items |
| `order` | `chapters` | `chronological` is one chapter, the span once; `shuffled` is a seeded shuffle with the date rules inert |
| `mixed_tiles` | yes | no: no featured picks, no anchors, every row a base row with the videos in the grid |
| `anchorLookahead` | 6 | packs anchors into feature rows; raises the share |
| `pullMaxGap` | 1.25 yr | fewer out-of-order pulls against more rows |
| `disorderWeight` | 2000 | chronology against video spacing |
| `videoMinRowGap`, `videoNudge` | 2, 12 | how hard spacing tries |
| `movingCap`, `maxBaseMoving` (`motion_density`) | 4, 2 (`normal`; `calm` 2, 1; `busy` 6, 3) | motion density against the sense of "occasional motion among stills" |
